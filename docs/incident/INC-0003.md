## 2. 根本原因分析

### 2-1. B-1（重説§3 miss）

```
クエリ: 「重説の３項目では家賃はいくらですか」
  ↓
extract_important_matters_section_id() → None  ← 正規表現が "重説の3項目" パターン未対応
  ↓
is_important_matters_question() → True（重説は検出）
  ↓
sidebar inject が G3（sid=None）でブロック
  ↓
vector search では §1(score=0.457) と §20(score=0.448) が top-k に入るが §3 は入らない
  ↓
§3 の月額費用表なしで LLM が生成 → 曖昧な答え
```

**追加 regression（PR-1c デプロイ後）:**  
PR-1c で inject コードが入ったものの、G4 の判定が「any important_matters in pool」だったため、§1/§20 が pool にいると §3 inject もブロックされた。

### 2-2. B-2（特約④ miss）

```
クエリ: 「違約金はいくらですか？」
  ↓
主検索: pdf_score_threshold=0.60
  特約条項 chunk: score=0.471 → threshold 以下で pdf_docs=[]
  第24条（遅延損害金）: score=0.477 → 同上
  ↓
contract_source retry: threshold=0.45 で再検索
  特約条項 chunk: score=0.471 → 通過するはずだが、
  retry query filter の heading_terms が「特約」を含まないため keyword_docs も不確実
  ↓
LLM は第24条（遅延損害金）のみを参照 → 特約④を見逃し「記載なし」と誤答
```

### 追加修正（2026-05-21）: G4 スコープ修正 + 特約④ inject

**コミット:** 5951a21

#### G4 バグ修正

PR-1c デプロイ後、§3 が regression した原因は G4 の判定範囲が広すぎたこと。

```python
# Before（バグ）: pool に any important_matters があれば inject をブロック
if any(str((d.metadata or {}).get("doc_kind") or "") == "important_matters" for d in other_docs):

# After（修正）: 対象 section_id と完全一致する IM chunk がある場合のみブロック
if any(
    str((d.metadata or {}).get("doc_kind") or "") == "important_matters"
    and str((d.metadata or {}).get("section_id") or "") == sid
    for d in other_docs
):
```

§1/§20 が pool にいても §3 inject が通るようになった。

## 4. inject フロー（最終版）

```
クエリ受信
    ↓
_hierarchical_search()  ← vector + BM25 hybrid, pdf_threshold=0.60
    ↓
contract_source_master_retry()  ← contract_source_q 時のみ, threshold=0.45
    ↓
kb_docs / other_docs に分離
    ↓
_inject_important_matters_section_if_needed()   ← G1-G6
  └─ G4: pool に同 section_id の IM chunk がある場合のみスキップ（修正後）
  └─ fetch: Chroma.get(doc_kind=important_matters, section_id=sid)
    ↓
_inject_tokuyaku_penalty_if_needed()            ← P1-P5（新規）
  └─ P3: pool に penalty chunk がある場合のみスキップ
  └─ fetch: Chroma.get(doc_kind=contract, cite_kind=special_terms)
    ↓
apply_master_document_boost()  ← inject 済み pool を reorder
    ↓
reranked[:rag_rerank_top_n]
    ↓
LLM 生成
```

## 9. 設計メモ（次回類似問題への参照）

**「vector score が閾値付近で不安定な chunk」への対処パターン:**

1. **boost（reorder）** — pool に chunk があるが順位が低い場合  
   → `apply_master_document_boost()` に条件ブロック追加
2. **inject（fetch）** — pool に chunk が入らない場合  
   → `fetch_master_by_metadata` or `fetch_master_by_cite_kind` + guard 関数
3. **retry クエリ拡張** — `_contract_source_master_retry` の `queries` リストに sub-query 追加

今回は §3 が inject パターン、特約④ が boost + inject（保険）の組み合わせ。

**G-guard / P-guard の命名規則:**  
- G = important_matters inject guards（G1-G6）  
- P = tokuyaku penalty inject guards（P1-P5）  
- 新規 inject を追加する場合は Q, R... で採番
